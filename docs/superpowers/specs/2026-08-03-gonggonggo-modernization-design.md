# GongGongGo 전체 개선 설계

작성일: 2026-08-03
상태: 사용자 승인 완료, 구현 전

## 1. 목적

현재 GongGongGo는 공고를 확인하고 상태를 분류할 수 있지만, 크롤링이 끝날 때까지 서버가 열리지 않고 JSON 동시 쓰기에 취약하며 QHD 화면의 사용성이 낮다. 이번 개선은 로컬 웹앱이라는 단순한 운영 형태를 유지하면서 서버 응답성, 크롤링 안정성, 데이터 무결성, 공고 판독성을 함께 높인다.

성공한 결과는 사용자가 컴퓨터 시작 후 기존 목록을 바로 열 수 있고, 백그라운드 크롤링 상태를 확인하면서 공고 상태를 안전하게 바꾸며, 넓거나 좁은 창에서 불필요한 시선 이동 없이 공고를 검토할 수 있는 것이다.

## 2. 범위

### 포함

- FastAPI 서버 즉시 시작과 시작 시 백그라운드 1회 크롤링
- 웹에서 수동 크롤링과 진행 상태 확인
- Async Playwright 기반 카테고리 동시 처리
- SQLite 저장소와 기존 JSON 선택적 마이그레이션
- 공고 상태 체계 개선
- 제목·날짜 구조화와 필터 정확도 개선
- 반응형 QHD 대시보드
- 웹에서 기관·직무 키워드와 실행 설정 편집
- 숨김/디버그 Windows 실행 경로
- 날짜별 로그와 14일 보존

### 제외

- 외부 접속, 배포와 인증
- 일정 간격 반복 크롤링
- OS 또는 브라우저 알림
- 별도 작업 큐나 크롤러 프로세스
- 데스크톱 앱 패키징

## 3. 전체 아키텍처

애플리케이션은 `127.0.0.1`에 바인딩하는 단일 FastAPI 프로세스로 운영한다. 서버의 lifespan에서 저장소와 크롤링 관리자를 준비하되, 크롤링 완료를 서버 준비 조건으로 삼지 않는다. Uvicorn이 요청을 받을 수 있게 된 뒤 시작 시 크롤링 작업을 예약한다.

크롤링 관리자는 Async Playwright Chromium 하나를 열고 카테고리마다 독립된 페이지를 사용한다. `asyncio` 동시성 제한으로 사용자가 저장한 `1`, `2`, `4`개 작업만 동시에 진행한다. UI에서는 구현 세부 용어 대신 `동시 크롤링 수`로 표현한다.

웹/API와 크롤러는 저장소 인터페이스를 통해 SQLite에 접근한다. 요청과 백그라운드 작업은 연결 객체를 공유하지 않는다. 쓰기 작업은 짧은 트랜잭션으로 제한하며 WAL과 busy timeout을 사용한다.

## 4. 구성요소

### 웹/API

- 대시보드와 설정 화면 제공
- 공고 목록 조회, 상태 변경, 영구 제거와 복원
- 크롤링 시작, 진행률 조회, 실패 카테고리 재시도
- 동시 작업 수, 브라우저 자동 열기, 기관·직무 키워드 저장

### 크롤링 관리자

- 앱 시작 시 1회 자동 실행
- 수동 실행과 개별 카테고리 재시도
- 실행 중 중복 요청 차단
- 전체 및 카테고리별 진행 상태 관리
- 전체 작업 종료 후 성공 결과 저장 조정

### 카테고리 크롤러

- 카테고리 하나와 독립 페이지 하나만 담당
- 수집 결과를 저장하지 않고 관리자에게 반환
- 개별 게시글 실패를 기록하고 가능한 범위에서 다음 항목 계속 처리
- 한 카테고리 실패가 다른 카테고리를 취소하지 않음

### 파서와 필터

- 제목 원문에서 모집인원 접두 문구, 기관, 고용 형태·경력, 직무를 분리
- 마감 원문을 정상 날짜, 상시, 미확인으로 분류
- 기관과 직무 영역에 서로 다른 키워드 목록 적용
- 파싱 실패 시 원문 보존과 명시적 fallback

### SQLite 저장소

- 스키마 준비와 1회 마이그레이션
- 공고 조회와 필드 단위 upsert
- 상태 변경, 설정, 실행 이력, 영구 제거 링크 관리
- 트랜잭션 경계와 동시 쓰기 정책 캡슐화

### 실행과 로그

- 작업 스케줄러에서 사용할 숨김 실행 경로
- 콘솔을 유지하는 디버그 실행 경로
- 두 경로 모두 같은 날짜별 파일 로그 사용
- 시작 시 14일 초과 로그 삭제

## 5. 데이터 모델

### `job_posts`

- 고유 ID
- 고유 source link
- category
- original title
- parsed institution, employment/career text, role text
- original deadline text
- nullable parsed deadline date
- deadline kind: `dated`, `open`, `unknown`
- status: `review_pending`, `planned`, `applied`, `excluded`
- new flag: 새로 수집된 검토 대기 공고인지 표시하는 boolean
- discovered, last seen, user-updated timestamps

화면의 한국어 상태명은 각각 `검토 대기`, `지원 예정`, `지원 완료`, `제외`다.

### `app_settings`

- concurrency: `1`, `2`, `4`; 기본 `2`
- open browser on startup: boolean; 기본 `false`

### 필터 키워드

대상 기관과 IT 직무 키워드는 별도 목록으로 저장한다. 현재 코드의 목록을 초기 기본값으로 사용한다. 입력 시 앞뒤 공백과 중복을 제거한다. 일치 방식은 기존 동작을 유지해 파싱된 기관명 또는 직무 항목 안의 대소문자 무시 부분 일치로 고정한다.

### `crawl_runs`와 카테고리 결과

- 시작·종료 시각
- 상태: 실행 중, 성공, 부분 실패, 실패
- 신규 공고 수
- 카테고리별 상태와 간결한 오류 요약

UI에는 마지막 실행과 카테고리 결과만 보여주고 상세 진단은 파일 로그에 둔다.

### `deleted_links`

- 제거된 source link
- 제거 시각

공고 본문을 영구 제거해도 링크 차단 기록을 남겨 재수집을 막는다. 설정 화면에서 차단 기록을 해제할 수 있다.

## 6. 마이그레이션

기존 `data/job_posts.json`은 원본 그대로 보존한다. 최초 SQLite 준비 시 `YYYY.MM.DD`로 정상 파싱되는 공고만 가져온다. 2026-08-03 조사 기준 전체 785건 중 정상 날짜 668건이 후보이며 날짜 미파싱 117건은 가져오지 않는다.

상태는 다음과 같이 변환한다.

| 기존 | 신규 |
|---|---|
| 대기 | 검토 대기 |
| 지원 예정 | 지원 예정 |
| 완료 | 지원 완료 |

마이그레이션 완료 표시를 남겨 다음 시작 때 반복하지 않는다. 이후 크롤링에서 새로 발견되는 `채용시마감`과 같은 공고는 `open`으로 저장할 수 있다.

## 7. 크롤링과 데이터 흐름

### 시작

1. 로그 초기화와 오래된 로그 정리
2. SQLite 스키마 준비와 필요한 경우 1회 마이그레이션
3. FastAPI 요청 수신 시작
4. 설정이 켜진 경우 로컬 상태 확인 엔드포인트의 성공 응답을 확인한 뒤 브라우저 열기
5. 백그라운드 크롤링 예약

### 실행

1. 저장된 동시 작업 수 읽기
2. Chromium 하나와 카테고리별 페이지 준비
3. 동시성 제한 아래 카테고리 실행
4. 진행률과 카테고리별 결과 갱신
5. 모든 카테고리가 종료된 뒤 성공 결과를 한 트랜잭션으로 반영
6. UI가 완료 상태를 감지하면 목록 갱신

크롤링 중 수동 실행 버튼은 비활성화하고 실행 요청을 예약하거나 기존 작업을 취소하지 않는다.

### 부분 실패

카테고리 하나가 실패해도 다른 카테고리는 계속한다. 성공한 카테고리 결과를 저장하고 전체 실행은 부분 실패로 기록한다. UI는 실패 카테고리와 간결한 사유 및 개별 재시도 동작을 제공한다.

## 8. 동시 수정 안전성

사용자의 상태 변경과 크롤러 반영은 서로 다른 필드의 짧은 트랜잭션이다.

- 상태 API는 status와 사용자 수정 시각을 갱신하고 new flag를 해제한다.
- 확인 API는 status를 유지한 채 new flag만 해제한다.
- 크롤러는 기존 행의 category, title, parsed fields, deadline, last seen만 갱신한다.
- 기존 행의 status와 new flag를 크롤러 기본값으로 갱신하지 않는다.
- 신규 insert에만 `검토 대기` 기본 상태와 new flag를 적용한다.
- source link 고유 제약으로 중복을 막는다.

따라서 같은 공고에 대한 두 쓰기가 겹치면 SQLite가 쓰기를 순서대로 처리하고, 서로 담당하지 않는 필드는 보존된다. 전체 행 교체 방식은 사용하지 않는다.

## 9. 제목 파싱과 필터링

원본 제목은 항상 저장한다. 가능한 경우 다음을 분리한다.

- 모집인원 등 앞쪽 접두 문구
- 기관명과 선택적 `채용` 접미어
- 고용 형태와 경력
- 마지막 괄호의 직무 목록

모집인원 접두 문구는 UI에서 숨긴다. 직무는 `/`, 쉼표 등 명확한 구분자로 항목화하되 모호한 복합 표현을 과도하게 분해하지 않는다.

표시 규칙은 다음과 같다.

1. 파싱된 기관명이 대상 기관 키워드와 일치하면 직무와 관계없이 표시한다.
2. 대상 기관이 아니면 파싱된 직무 항목에 IT 키워드가 있어야 표시한다.
3. 일반 기관은 일치한 직무 항목만 화면에 표시한다.
4. 대상 기관은 IT 일치 항목이 있으면 이를 강조하고, 없으면 파싱된 전체 직무를 표시한다.
5. 직무 파싱에 실패한 대상 기관은 원문 제목으로 표시한다.
6. 직무 파싱에 실패한 일반 기관은 필터 결과에서 제외한다.

키워드 설정 변경은 저장된 파싱 결과에 즉시 다시 적용되며 재크롤링이 필요 없다.

## 10. 날짜 처리와 영구 제거

마감일은 다음 세 유형이다.

- `dated`: 확정 날짜로 변환 가능
- `open`: 채용 시 마감, 상시채용, 수시채용처럼 명시적으로 기한이 없음
- `unknown`: 여러 날짜, 오염 문자열 등 안전하게 해석할 수 없음

`8/5`처럼 의미가 명확한 값은 현재 연도 규칙으로 보정할 수 있다. 여러 날짜나 의미가 불분명한 값은 추측하지 않고 `unknown`으로 둔다.

수집 결과를 저장할 때 마감일이 오늘보다 지난 `dated` 공고는 기존 저장분과 신규 수집분 모두 제거한다. 오늘 마감 공고와 `open`, `unknown` 공고는 유지한다. 자동 만료는 사용자 영구 제거가 아니므로 링크 차단 기록을 남기지 않는다.

제외 목록의 모든 공고는 영구 제거할 수 있다. 상시와 미확인 공고에는 상태 이동을 거치지 않고 바로 영구 제거할 수 있는 동작도 제공한다. 제거 전 확인하고, 제거 후 본문은 목록에서 삭제하되 링크 차단 기록을 남긴다. 사용자가 설정에서 차단을 해제하면 해당 공고는 다음 크롤링에서 다시 발견될 때 신규 공고로 들어올 수 있다.

## 11. UI/UX

### 넓은 화면

- 중앙 정렬, 콘텐츠 최대 폭 약 1,600px
- `진행 중`과 `보관함` 묶음 전환
- 진행 중은 검토 대기와 지원 예정 목록을 2열로 표시
- 보관함은 지원 완료와 제외 목록을 2열로 표시

### 좁은 화면

약 1,400px 아래의 실제 콘텐츠 너비에서는 네 상태 탭 중 하나만 표시한다. QHD 화면을 절반으로 나눈 창에서도 두 긴 목록을 위아래로 쌓지 않는다.

### 공고 카드

- 기관명을 가장 강하게 표시
- 고용 형태와 경력을 작은 배지로 표시
- 필터된 직무를 읽기 쉬운 구분자로 표시
- 마감은 날짜와 D-day로 표시
- 상태 이동 버튼을 같은 카드 안에 배치해 시선 이동을 줄임
- 새로 수집한 검토 대기 공고는 `NEW` 배지와 `확인` 버튼을 표시하고 목록 상단에 최신순으로 배치
- `확인`이나 상태 이동 시 `NEW`를 해제하며, 제목 링크 열기는 확인으로 간주하지 않음
- 긴 직무는 줄임 표시하되 전체 내용을 확인할 수 있게 함
- 제외 직후 실행 취소 제공

상단에는 검색, 카테고리 필터, 마감순 정렬, 마지막 크롤링 결과와 현재 진행률을 둔다. 설정 화면에는 동시 작업 수, 브라우저 자동 열기, 기관·직무 키워드 목록과 제거 링크 관리만 둔다.

## 12. 실행과 로그

- `ggg_startup.bat`: 기존 작업 스케줄러 경로를 유지하는 얇은 숨김 실행 래퍼
- `ggg_startup.vbs`: BAT를 다시 호출하지 않고 서버를 숨김 상태로 직접 실행
- `ggg_debug.bat`: `--debug`로 서버를 실행해 콘솔과 실시간 로그를 유지하고, 크롤링 중 Playwright Chromium GUI를 표시하는 문제 확인용 실행기

애플리케이션 로깅은 콘솔과 날짜별 파일에 동시에 연결한다. 숨김 실행에서는 콘솔이 보이지 않지만 파일은 동일하게 기록된다. 일반 실행의 크롤러는 headless 모드를 유지하고 `--debug` 실행에서만 Chromium 창을 표시한다. 서버 시작 시 14일보다 오래된 로그 파일을 삭제한다.

작업 스케줄러가 BAT를 계속 가리킬 수 있으나 콘솔의 순간적인 깜빡임까지 피하려면 사용자가 VBS를 직접 대상으로 변경할 수 있다.

## 13. 오류 처리

- 네트워크 실패는 웹서버를 중단하지 않는다.
- 사용자에게는 간결한 오류와 재시도 동작을 제공한다.
- 상세 예외와 스택 정보는 파일 로그에 기록한다.
- 설정값은 허용 범위와 중복 여부를 검증한다.
- 파싱 실패는 예외가 아니라 명시적 결과로 처리한다.
- DB가 잠시 사용 중이면 busy timeout 안에서 기다리고, 실패 시 요청을 명확히 실패시킨다.

## 14. 테스트와 성공 기준

### 단위 테스트

- 제목 정상, 접두 문구, `채용` 접미어 변형, 파싱 실패
- 정상 날짜, 연말 보정, 상시 문구, 미확인 값
- 기관 예외와 일반 기관 IT 직무 필터
- 다중 직무에서 일치 항목만 선택
- 상태 매핑과 정상 날짜만 가져오는 마이그레이션

### 저장소와 동시성 테스트

- 크롤러 upsert가 기존 사용자 상태를 보존
- 상태 변경이 크롤러 필드를 훼손하지 않음
- 링크 고유 제약과 영구 제거 차단
- 설정 저장과 재시작 후 로드

### 관리자와 API 테스트

- 실행 중 중복 실행 차단
- 동시성 설정 준수
- 부분 실패 후 성공 결과 저장
- 실패 카테고리 개별 재시도
- 서버가 크롤링 완료 전에 응답

### UI와 실행 검증

- 넓은 화면의 두 목록과 좁은 화면의 단일 탭
- 상태 이동, 제외 실행 취소와 복원
- 숨김 실행 시 프롬프트가 남지 않음
- 디버그 실행 시 콘솔과 파일 로그 생성
- 14일 초과 로그 정리

완료 기준은 관련 자동 테스트가 통과하고, 실제 Windows 시작 경로에서 서버 즉시 응답·백그라운드 크롤링·설정 유지·동시 상태 변경이 확인되는 것이다.
