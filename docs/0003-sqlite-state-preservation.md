# SQLite와 사용자 상태 보존

결정:

- 채용과 뉴스는 `data/gonggonggo.db`의 독립 테이블을 사용한다. 요청과 작업은 연결을 공유하지 않으며, 쓰기는 짧은 트랜잭션과 WAL·5초 busy timeout을 사용한다.
- 크롤러는 기존 공고의 수집 소유 필드만 갱신한다. 사용자의 상태·핀·확인 상태·상태 수정 시각을 덮어쓰거나 기존 행 전체를 교체하지 않는다.
- JSON 원본이 있으면 정확한 `YYYY.MM.DD` 마감일 공고만 한 번 마이그레이션한다. `대기/지원 예정/완료`는 `검토 대기/지원 예정/지원 완료`로 변환하며 원본은 수정·삭제하지 않는다. 기존 DB와 마이그레이션 행은 NEW로 만들지 않는다.
- 저장 시 오늘보다 마감일이 지난 날짜형 공고를 정리한다. 오늘 마감·상시·미확인 공고는 유지한다. 자동 만료는 재수집 차단을 남기지 않는다.
- 사용자의 영구 삭제는 공고 본문을 제거하고 최소 링크 차단 기록을 남긴다. 차단을 해제하면 다음 수집에서 신규 공고로 들어올 수 있다.
- 백업·이전은 서버를 종료한 뒤 DB와 남은 WAL sidecar를 함께 복사하며, JSON 원본이 있으면 함께 보관한다.

이유: 크롤링과 사용자 조작이 겹쳐도 사용자 결정을 보존하고, 마이그레이션·삭제·백업 과정에서 데이터 손실과 원치 않는 재등장을 방지하기 위해서다.
