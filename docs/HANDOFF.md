# GongGongGo 인수인계

최종 갱신: 2026-08-03

## 현재 단계

브레인스토밍과 전체 설계 승인이 끝났다. 구현은 시작하지 않았다. 다음 세션은 사용자가 작성된 설계 문서를 검토하고 승인한 뒤 `superpowers:writing-plans`를 사용해 상세 구현 계획을 작성해야 한다.

정식 설계 문서: `docs/superpowers/specs/2026-08-03-gonggonggo-modernization-design.md`

## 현재 코드 구조

- `main.py`: FastAPI 라우트, 제목 필터, JSON 상태 변경, 앱 시작 전 동기 크롤링을 한 파일에서 담당
- `src/gongjoonmo_crawler.py`: Naver Cafe 카테고리 4개를 순차 크롤링하고 JSON을 원자적으로 교체
- `templates/index.html`: 인라인 CSS/JavaScript 기반의 상태별 테이블
- `data/job_posts.json`: 운영 중인 공고와 상태 데이터
- `ggg_startup.bat`, `ggg_startup.vbs`, `ggg_startup.fish`: 실행 스크립트
- `test.py`: 자동 테스트가 아닌 필터 실험 파일

의존성 선언 파일과 실질적인 자동 테스트는 없다.

## 조사에서 확인한 문제

- 크롤링이 끝나야 Uvicorn이 시작되어 웹 화면을 바로 열 수 없다.
- 크롤러와 웹 상태 변경이 같은 JSON을 쓰므로 향후 백그라운드 실행 시 변경 손실 위험이 있다.
- 카테고리는 순차 처리되며 게시글 하나의 예외가 전체 크롤러를 조기 종료시킨다.
- 크롤링 진행 상태와 최근 실행 결과를 웹에서 확인할 수 없다.
- `is_target_post`의 조기 `return` 아래 조건 코드는 실행되지 않는다.
- 제목 전체에 기관과 직무 키워드를 적용해 역할 영역 외의 단어가 필터에 영향을 줄 수 있다.
- 현재 UI는 QHD 전체 화면에서 공고명과 상태 버튼 사이가 지나치게 멀다.
- 현재 Windows VBS는 숨김 서버를 실행한 뒤 별도의 로그 PowerShell 창을 연다.

## 승인된 핵심 결정

- 로컬 웹앱과 `127.0.0.1` 바인딩 유지
- 서버 즉시 시작 후 백그라운드에서 시작 시 1회 크롤링
- 수동 크롤링 버튼 제공, 실행 중에는 중복 실행 차단
- Async Playwright, Chromium 하나, 카테고리별 페이지와 동시성 제한 사용
- 동시 작업 수 `1/2/4`, 기본값 `2`, 웹 설정에서 저장
- 브라우저 자동 열기 설정, 기본값 `끔`
- SQLite 사용과 기존 JSON의 선택적 마이그레이션
- 상태명은 `검토 대기`, `지원 예정`, `지원 완료`, `제외`
- 넓은 화면은 `진행 중`과 `보관함` 묶음으로 두 목록 표시
  - 진행 중: 검토 대기 + 지원 예정
  - 보관함: 지원 완료 + 제외
- 좁은 화면은 네 상태 중 하나만 탭으로 표시
- 콘텐츠 최대 폭 약 1,600px로 제한해 QHD에서도 공고와 버튼을 가깝게 배치
- 제목을 기관, 고용 형태·경력, 직무로 구조화하고 실패 시 원문 표시
- 모집인원 접두 문구는 화면에 표시하지 않음
- 대상 기관 키워드와 IT 직무 키워드를 웹에서 편집
- 키워드는 해당 파싱 영역 안에서 대소문자를 무시한 부분 일치로 판정
- 대상 기관이면 직무와 관계없이 표시
- 일반 기관이면 파싱된 직무에 IT 키워드가 있을 때만 표시하고 일치 직무만 노출
- 크롤링 중 사용자 상태 변경을 허용하며 크롤러는 상태 필드를 수정하지 않음
- 카테고리 하나가 실패해도 나머지는 계속하고 성공 결과는 저장
- 전체 작업 완료 후 결과를 한 번에 반영
- 날짜는 정상 날짜, 상시, 미확인으로 분류
- 제외 목록의 모든 공고는 영구 제거할 수 있고 상시/미확인 공고에는 바로 제거 동작도 제공
- 영구 제거는 링크 차단 기록으로 재수집을 막고, 차단 해제 후에는 다음 크롤링에서 신규로 들어올 수 있음
- 날짜별 로그를 남기고 서버 시작 시 14일 초과 로그 삭제
- 작업 스케줄러용 숨김 실행과 콘솔 유지 디버그 실행을 분리

## 기존 데이터 조사 결과

2026-08-03 기준 `data/job_posts.json`에는 785건이 있었다.

- `YYYY.MM.DD` 정상 날짜: 668건
- 날짜 미파싱: 117건
- 유연한 제목 패턴으로 기관/본문 파싱 가능: 775건
- 마지막 직무 괄호 파싱 가능: 762건
- 제목 구조 전체 실패: 10건

날짜 미파싱 117건에는 `채용시마감` 77건, `채용시 마감` 6건, `채용시까지` 5건과 기타 상시·오염 값이 포함되어 있었다.

기존 대상 기관 공고는 12건이었으며 현재 IT 키워드를 직무에만 적용하면 2건이 일치하고 10건이 불일치했다. 사용자는 이 결과를 확인한 뒤 기관 일치 공고를 직무와 관계없이 계속 표시하기로 결정했다.

## 마이그레이션 규칙

- 정상 날짜 668건만 마이그레이션 후보로 삼는다.
- 날짜 미파싱 117건은 SQLite로 가져오지 않는다.
- `대기`는 `검토 대기`, `지원 예정`은 그대로, `완료`는 `지원 완료`로 변환한다.
- JSON 원본은 수정하거나 삭제하지 않는다.
- 마이그레이션 완료 여부를 기록해 재시작 때 중복 수행하지 않는다.
- 이후 새로 수집되는 상시 공고는 `상시`로 정상 저장할 수 있다.

## 동시 수정 불변 조건

- UI 상태 변경은 해당 행의 상태와 수정 시각만 갱신한다.
- 크롤러 upsert는 제목, 카테고리, 마감 정보, 마지막 확인 시각 등 크롤러 소유 필드만 갱신한다.
- 기존 행의 상태를 insert 기본값이나 크롤링 결과로 덮어쓰지 않는다.
- 링크에 고유 제약을 둔다.
- SQLite는 WAL, busy timeout, 작업별 연결과 짧은 트랜잭션을 사용한다.

## 구현 범위 밖

- 외부 네트워크 접속과 배포
- 로그인 및 사용자 권한
- 일정 간격 반복 크롤링
- OS·브라우저 알림
- 별도 작업 큐 또는 크롤러 프로세스

## 다음 세션 체크리스트

1. 사용자에게 설계 문서 검토 승인을 받는다.
2. `superpowers:writing-plans`를 읽고 상세 구현 계획을 작성한다.
3. 구현 계획에서 테스트 우선 순서, SQLite 마이그레이션, 비동기 크롤러 전환, API/UI, 실행 스크립트 순서를 명시한다.
4. 구현 전 현재 JSON을 변경하지 않는 테스트 전략을 확정한다.
5. 구현이 실제 완료된 뒤 README와 이 문서의 현재 단계를 갱신한다.
